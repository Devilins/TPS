## Локальный тест-стенд — полностью поднят и работает (Windows, без Docker)

1. **Зависимости** — всё стоит в poetry venv (opencv, celery 5.6.3,
   ai-edge-litert 2.2.0, redis-py). `poetry install` не нужен.
2. **Postgres** — нативно на хосте, `localhost:5432`.
3. **Миграции** — `report_ocr.0001_initial` применена, модели не разъехались.
   Побочный фикс: у `tph_system` было 5 "непримененных" миграций (`0002`–`0006`),
   чей эффект уже был физически в схеме под другим именем в `django_migrations`
   (след старого сквоша) — починено через
   `migrate tph_system 0006_... --fake` (не удаление файлов, не merge в initial).
4. **Redis** — поднят пользователем в WSL2 Ubuntu (`sudo apt install redis-server`,
   работает как systemd-сервис на `6379`). Виден с Windows-хоста через WSL2
   localhost forwarding — проверено (`redis.Redis(host="localhost").ping() -> True`).
5. **`.env`** — добавлены `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND=redis://localhost:6379/0`.
   **Это только для локального теста** — на проде ничего менять не надо, там
   сработает дефолт `settings.py` (`redis://redis:6379/0`, имя докер-сервиса),
   да и `.env` на проде — отдельный файл (в `.gitignore`), с локальным никак
   не связан.
6. **Celery-воркер** — запущен нативно на Windows: `poetry run celery -A Dj_TPS
   worker --loglevel=info -P solo` (флаг `-P solo` обязателен на Windows —
   дефолтный prefork-пул там не работает). На момент последнего сохранения
   контекста воркер был запущен в фоне (id таска `bjz8ns1lh` в рамках этой
   Claude Code сессии) и подключён к Redis. Если сессия/комп перезапускались —
   его нужно поднять заново той же командой.
7. Пользователь прогнал реальную загрузку через интерфейс (`/report-ocr/upload/`)
   — интерфейс работает целиком (форма → Celery-таск → страница результата).

## Найденный и исправленный баг: детекция угловых меток

На реальном тестовом фото (`ReportUpload.id=1`, точка Joki Joya JJGgr,
`media/report_ocr/uploads/2026/09/23/IMG20260923005059.jpg`) метки не
находились: `MarkersNotFound: Не удалось выбрать 4 угла листа (score=1e18)`.

Диагностика (см. `pipeline/markers.py::_find_square_blobs` /
`_best_quad`): реально на фото 3 нормальных угла + 1 угол (левый нижний)
отбраковывался по порогу контраста (`std=33.2` против требуемых `std>=38` —
из-за неравномерного освещения именно в этом углу кадра), при этом
правый-нижний угол детектировался ДВАЖДЫ (внешний+внутренний контур одной и
той же метки — блик/неоднородность внутри чёрного квадрата на
adaptiveThreshold). В сумме получалось формально "4 кандидата", но
геометрически невалидных (2 дубля одной точки + пропуск другой).

**Фикс (сделан и проверен на этом же фото):**
- `_dedupe_candidates()` — схлопывает кандидатов с центрами ближе 15px
  (дубли контуров одной метки), оставляет более крупный.
- Двухпроходный порог контраста: сначала строгий `_STRICT_MIN_STD=38`
  (как раньше — чтобы не ловить тени/текстуру стола), и только если после
  дедупликации набралось <4 меток — повторный проход с
  `_RELAXED_MIN_STD=25` для недостающих углов.
- Проверено на `manage.py`-independent скрипте прямо на реальном фото id=1:
  `detect_and_warp()` теперь отрабатывает успешно (`warped shape:
  (1782, 2520, 3)` — ровно ожидаемый размер).
- **Не проверено на других фото** — порог `25` подобран по одному кадру,
  надо будет посмотреть на выборке из нескольких реальных фото (особенно
  в плохом освещении), не начал ли он ловить лишнее. Если понадобится ещё
  тюнинг — обсуждали как fallback вариант CLAHE/локальную нормализацию
  контраста перед adaptiveThreshold (пока не делали, overkill для первого
  прохода).
- `ReportUpload.id=1` в БД всё ещё висит со статусом `error` (обработан ДО
  фикса) — **переобработку не запускали**, ждали решения пользователя:
  либо `process_report.delay(1)` вручную, либо новая загрузка через интерфейс.

## Визуал: report_ocr переведён на дизайн-систему tph_system

По результатам ревью `tph_system/base.html` + `tech.html` / `check_reports.html`
/ `tech_update.html` / `rep_update.html` / `tables.py` (Bootstrap 5 + свой
`styles.css`, карточки `.card.shadow`, таблицы `table-sm table-hover
table-bordered align-middle caption-top` со sticky-шапкой, `django_filters`
для фильтров, `Paginator` для пагинации, паттерн `current_filter_params`
для "истории" фильтра между списком/детейлом/удалением).

Решения пользователя: **навигацию в `tph_system/base.html` пока не трогаем**
(добавит сам позже, как удобнее), **upload — отдельная страница** (не модалка),
**список — полный паттерн** с фильтрами (точка/дата/статус) и пагинацией.

Сделано:
- `forms.py` — Bootstrap-виджеты, `report_date` на `FengyuanChenDatePickerInput`
  (тот же датапикер, что везде в TPS).
- Новый `filters.py` — `ReportUploadFilter` (location/report_date/status) по
  образцу `CheckReportsFilter`.
- `views.py` — `list_view` с фильтром+`Paginator(25)`; `title` в контексте
  всех view; `detail_view` отдаёт `current_filter_params`; новый
  `ReportUploadDeleteView` (`LoginRequiredMixin` + `DeleteView`, как
  `TechDeleteView` — `get_success_url()` на список с сохранённым фильтром,
  `form_valid()` дополнительно удаляет файл фото из media перед удалением
  записи).
- `urls.py` — добавлен `report/<int:pk>/delete/` → `report_ocr:delete`.
- `upload.html` — карточка+форма по образцу `rep_update.html`.
- `list.html` — полный паттерн: карточка, фильтр-форма, sticky-таблица,
  подсветка строк по статусу, пагинация, кнопка «Загрузить отчёт». Колонка
  «Открыть» убрана, добавлена «Обработано» (`processed_at`), в
  `created_at`/`processed_at` добавлены секунды. Ссылки на детейл несут
  `?{{ current_filter_params }}`.
- `detail.html` — статус/совпадения через Bootstrap-бейджи вместо текста,
  `needs_review` через `table-warning`. В шапке карточки — кнопки «Открыть
  исходное фото» (теперь кнопка, не голая ссылка), «Назад» (на список с
  сохранённым фильтром), «Удалить» (на страницу подтверждения).
- Новый `upload_delete.html` по образцу `tech_delete.html`.
- Старый самодельный `report_ocr/templates/base.html` удалён — все шаблоны
  теперь `{% extends 'tph_system/base.html' %}` напрямую.

**Проверено** (Django test client, без порчи реальных данных): `manage.py
check` чист; список/детейл/страница удаления рендерятся (200) с фильтром и
без; фильтр по статусу и пагинация с `page=` работают; полный цикл удаления
(файл + запись, редирект с сохранением фильтра) проверен на отдельной
одноразовой тестовой записи — реальную id=1 не трогали.
