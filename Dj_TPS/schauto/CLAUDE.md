# schauto — полуавтоматическое планирование выездных фотографов

> Контекст приложения. Читай перед любой доработкой `schauto`, обновляй по ходу разработки (статус этапов,
> решения, открытые вопросы). Общий контекст проекта — `../../CLAUDE.md` (корень репозитория).
> Последнее обновление: 2026-10-28 (этапы 0–5, откат применения, ретушёр в Joki Joya, быстрая загрузка из таблиц через сервисный аккаунт и подтверждение пограничных проблем вручную, недельная нагрузка по «Заказам» и заказы с несколькими фотографами («Имя + Имя») написаны, не закоммичены; миграции 0004–0012 применены только к локальной dev-БД). **Файл обновляется в конце каждого шага разработки.**

## 1. Задача

Сейчас сотрудники вносят заказы в Google-таблицы, руководитель вручную назначает выездных фотографов и ретушёров
(в столбцы «Фотограф» / «Ретушер»). Нужно: по кнопке импортировать заказы из таблиц, **предложить распределение**
(навык исполнителя, сложность центра, время в пути между центрами и др.), после подтверждения руководителем —
проставить выездных в `tph_system.Schedule` (роль «Выездной фотограф») и вписать «Имя Фамилия» в таблицу.
Интеграция запускается кнопкой, не автоматически. Язык кода, UI, комментариев и сообщений — русский.

| «МЕГА» после даты на «Облака JJ» — историческая пометка: у Мега теперь свой лист | пометка просто сохраняется в замечаниях |
| **`Venue` (центр) отдельно от `Store`**; в `Venue` точки «дублируются» | `Store` = центр с фототочкой и штатом (и параметрами ЗП); `Venue` = любой центр, куда приезжают выездные. Связь `Venue.store` — необязательная |
| У `Venue` есть **сложность 1–10** | влияет на распределение вместе с навыком |
| Навык (`Staff.skill_score`, 1–10) работает как **приоритет**: чем выше навык, тем более длинные, сложные и многочисленные заказы | + учитывать сложность центра. В солвере: нехватка навыка штрафуется сильно, избыток — почти нет, доля нагрузки растёт с навыком (§6). Сложность центров владелец проставил сам (2026-10-27) |
| Типы `Staff.staff_type`: Штат / Выездной / Ретушер. Планировщик назначает только Выездных (фотографы) и Ретушёров | Штат не трогаем |
| `Staff.retouches_own` (по умолчанию да): выездной сам обрабатывает фото; если нет — нужен отдельный Ретушер. Столбец «Ретушер» есть **только в таблице JJ**; в LL ретушёр не планируется | «исходники» в «Ретушер» = клиент купил исходники, ретушь не нужна (подтверждено; бывает редко) |
| **Лимит заказов в день задаётся в карточке сотрудника** (`Staff.max_orders_per_day`; обязателен для типа «Выездной» — проверка в `StaffForm`). Значения «по умолчанию» нет; выездной без лимита в автоплан не попадает (и подсвечивается на `/schauto/`) | кто-то берёт 5+, кто-то 1–2 |
| **Буфер 15 мин** между заказом и поездкой/началом | параметр планировщика |
| **Назначенное вручную не трогаем, но учитываем** при распределении (занятость, лимит, дорога) | |
| **Выездного НЕ ставим, если в «Графике выходов и отпусков» (`WorkVacSchedule`) на этот день стоит «Отпуск», «Отгул» или «Больничный». Пустой статус, «Работает» и отсутствие записи — ставим.** Смены в `Schedule` доступность **не** ограничивают | 2026-10-27, решение владельца (на тот же день ненадолго было «только при отметке Работает» — отменено). `time_availiable` разбирает `availability.py` (§6): «с 15:00», «до 18:00», «11:00-22:00», «До 14:30 и с 18:30», «Занят 17:00-19:00», «весь день», «с 12:30/13:00» (берётся более позднее). Неразобранное («ПОЛ ДНЯ») = в этот день не назначаем + предупреждение |
| **В `Schedule` пишем только заказы центров с фототочкой** (`Venue.store` заполнен). Для центров без фототочки в `Schedule` не пишем — достаточно записи в Google-таблицу | подтверждено 2026-10-21 |
| Списки в `schauto` (центры, маршруты, заказы) — **по 40 строк** на странице (`views.PAGE_SIZE`); на экране «Сопоставления» таблицы с формами показывают первые 40 строк | 2026-10-23 |
| **Адрес центра хранится в `Venue.address`** (редактируется в «Центрах»; на `/schauto/` считается число центров без адреса) | 2026-10-23, предложение владельца |
| `Venue.store` берётся **только из фототочек в статусе «Действующая»** (`limit_choices_to`; команда заведения центров привязывает точку сама по бренду и названию, если подходит ровно одна действующая) | 2026-10-23 |
| **Заказ с разбивкой времени** («14:00-15:00 и 15:30-16:30»): в «Заказах» показывается полный набор интервалов, а не «от первого начала до последнего конца»; время работы = сумма интервалов (+ продление). Если перерыв между интервалами **от 60 мин** (`SPLIT_GAP_MINUTES`), части заказа можно отдавать **разным фотографам** (так лучше распределяется нагрузка), а в перерыв фотографу — вставить другой заказ (редко: например, перерыв 1,5 ч в LL Гагаринский и заказ на 1 ч в JJ Гагаринский). Перерыв короче часа — фотограф остаётся на заказе | 2026-10-23; разбиение делает планировщик (этап 3), в данных уже есть `PhotoOrder.slots` и `parts`. **Решение владельца 2026-10-28: вариант C — планировщик делит заказы сам; в ячейку «Фотограф» пишется «Имя + Имя» (так двух фотографов и пишут в таблицах), время в ячейку не пишется; ЗП за части — позже, вместе с расчётом ЗП выездным** |
| **LL: «Катерина 89688649620» в ячейке «Фотограф» — это руководитель, а не исполнитель** (значение по умолчанию); имя фотографа дописывается после него. Последние (и первые) цифры телефона в таблице бывают с опечатками — убираем «Катерина» + любой номер от 7 цифр. Остаток ячейки — имя фотографа; если остатка нет, заказ свободен | `gsheet.MANAGER_NAMES`, `parsers.strip_manager`. «Катерина» без телефона — обычное имя |
| В `Schedule.work_time` писать **начало первого заказа** (`HH:MM`, поле на 20 символов); полные интервалы, часы и центры каждого заказа хранит schauto | |
| Маршруты — вручную (CSV/UI), на общественном транспорте, **все варианты**, направленные пары; в расчёте берётся минимум по паре. LL и JJ «Гагаринский» — 5 мин (можно 0) | |
| Нет маршрута для пары — не блокируем, считаем консервативным значением по умолчанию и помечаем в плане | (этап 3) |
| Персональные данные клиентов из таблиц **не импортируем** (заказчик, телефон, именинник, ссылки на фото, пожелания); телефоны сотрудников из ячейки «Фотограф» отбрасываем | нужны: лист, дата, время, комментарий (доп. время), «Фотограф», «Ретушер», адрес выезда |
| **При записи в таблицу Joki Joya фотограф, который сам обрабатывает фото (`Staff.retouches_own`), вписывается и в столбец «Ретушер»** (2026-10-28). Пустую ячейку заполняем; уже указанный ретушёр и «исходники» не трогаем (замечание, не ошибка); фотограф без самообработки — «Ретушер» пуст, в итоге замечание «нужен отдельный ретушёр»; в Laserland столбца нет | выбор отдельного ретушёра — этап 6 |
| **Применение распределения** (2026-10-27): черновик правится в UI (смена фотографа в каждой строке) → «Применить» запускает проверки: у всех частей есть фотограф; заказ в таблице не изменился с расчёта; в графике выходов стоит «Работает» и время подходит; фотограф успевает между заказами (дорога + буфер, без пересечений); дневной лимит не превышен. Всё OK → запись в Google-таблицы → запись в `Schedule` (только центры с `Venue.store`) → уведомление «все проверки успешны, фотографы проставлены в график и в Google-таблицы». **Дневной лимит заказов (`Staff.max_orders_per_day`, с учётом назначенного вручную в таблицах) блокирует применение.** **Проблемы двух видов (2026-10-28):** *блокирующие* (подтвердить нельзя, меняется исполнитель) — нет фотографа, заказ изменился или занят, фотограф не работает, отпуск/отгул/больничный, время в графике не разобрано, пересечение заказов, дневной лимит; *подтверждаемые вручную* — фотографу не хватает минут на дорогу и запас между заказами (пограничные 5–10 мин: человек знает, что он успеет) и заказ выходит за время из графика выходов («с 15:00»). Подтверждает руководитель галочкой «Успеет, подтверждаю» в строке или массово «все, где не хватает не больше N мин» (по умолчанию 10); применение возможно, когда блокирующих нет и всё подтверждаемое подтверждено. Подтверждение действует, пока не изменилась ситуация (фотограф, части, цифры «нужно/есть», текст графика); подтверждённое попадает в сообщения, журнал и «Историю применения» | в `Schedule` пишутся только заказы, которые удалось вписать в таблицу (график и таблица не расходятся); `Schedule.update_or_create` не используется — только `get_or_create`, уже существующая смена не меняется |
| **Расчёт ЗП выездным — потом**, отдельно от `tph_system/funcs.py` (`sal_calc`) | поэтому schauto хранит часы каждого заказа |
| Google: **используем учётку Google (сервисный аккаунт)** — для записи в таблицы (этап 5) и **для чтения (загрузка заказов, с 2026-10-28)**: публичный доступ по ссылке больше не нужен, его можно закрыть (в таблицах телефоны клиентов). Публичный CSV-экспорт остался только запасным путём, если ключ не настроен (в отчёте загрузки тогда есть примечание) | см. §5 |

## 3. Модели (`models.py`)

Сделано (миграции `schauto/0001`–`0005`):
- `Venue` — name (уникальное, бренд в названии: «Гагаринский LL» / «Гагаринский JJ»), brand (LL / JJ / OT «Другой центр»),
  **address** (адрес центра: метро/улица, дом, торговый центр — основа для маршрутов и ссылок в карты; координаты появятся вместе с выбором способа расчёта маршрутов, §11),
  difficulty (1–10, по умолчанию 5), store (FK→`tph_system.Store`, null), `sheet_tab_name` (имя листа **в таблице своего бренда**;
  unique(brand, sheet_tab_name)), is_active, date_upd, user_edited. Таблица заказов центра определяется по `brand`
  (`gsheet.get_sheet_id(brand)`); у `OT` листа нет. **Закрытые центры (Азовский LL и т.п.) нужно деактивировать** — это защищает от импорта устаревших листов.
- `Route` — from_venue, to_venue, description (вариант), duration_min (0–600); unique(from, to, description), запрет from == to.
- `VenueAlias` — фрагмент адреса (нормализованный `parsers.norm_place`) → `Venue`; применяется к листу «ВЫЕЗДЫ»; побеждает самый длинный фрагмент.
- `StaffAlias` — имя из ячейки (нормализованное `parsers.norm_person`; телефон и маркер руководителя LL уже отброшены) → `Staff`; `staff = NULL` значит «игнорировать» (пометки вроде «ищем»).
  Автоматически сопоставляются только полные «Имя Фамилия»/«Фамилия Имя» работающих сотрудников; одиночные имена («Дина») — только вручную.
- `PhotoOrder` — заказ из строки листа: brand (таблица), tab_name, sheet_gid, sheet_row, **fingerprint** (unique вместе с brand+tab_name),
  venue (null для невыясненных выездов) / place_raw (адрес храним, **только пока центр не определён**), date, time_start/time_end,
  **slots** (все интервалы заказа `[["14:00","15:00"],["15:30","16:30"]]`; time_start/time_end — границы всего заказа), extra_minutes (продление, относится к концу последнего
  интервала), raw_time, notes (замечания разбора), photographer_raw / retoucher_raw (очищенные имена из таблицы; в «Фотографе» — один человек или несколько через « + », до 120 символов), `photographers` (M2M, миграция 0011: сопоставленные сотрудники заказа с НЕСКОЛЬКИМИ фотографами; у заказа с одним исполнителем пусто — он в `photographer`),
  photographer / retoucher (FK `Staff`), no_retouch, status (open / assigned / needs_fix / gone), first_seen_at, last_seen_at.
  Право `schauto.import_orders` (загрузка + экран сопоставлений). Свойства: `slot_times`, `intervals_display`, `parts` / `can_split` (части для разных фотографов),
  `duration_minutes` (сумма интервалов + продление), `sheet_url` (ссылка на строку в таблице).

Сделано в `tph_system.Staff` (миграция `tph_system/0009_staff_planning_fields`): `staff_type`, `skill_score` (1–10; обязателен для Выездного и Ретушёра),
`retouches_own`, `max_orders_per_day` (обязателен для Выездного).

Сделано в этапе 3 (миграция `schauto/0006`):
- `PlanRun` — один расчёт: период, статус (`draft`), кто и когда, `config` (параметры солвера), `summary` (итоги), `warnings`, `fixed` (назначенное вручную и учтённое как занятость), `confirmed` (миграция 0010: проблемы, подтверждённые руководителем вручную, `{подпись: {text, by, at}}`; подпись `gap|<фотограф>|<часть1>|<часть2>|<нужно>|<есть>` или `window|<фотограф>|<дата>|<начало-конец>|<хеш текста графика>`). Права: стандартные + объявленное `schauto.run_planning` (расчёт; просмотр — `view_planrun`).
- `Assignment` — часть заказа в расчёте: `plan`, `order`, `part_no`/`parts_total`, дата, `start_min`/`end_min`, `staff` (пусто = не распределена), `need`, `cost`, `candidates`, `reasons` / `alternatives` / `rejected` (объяснения). unique(plan, order, part_no).

Запланировано:
- к `Assignment` на этапах 4–5 добавятся ссылка на созданный `Schedule` и **раздельные статусы** записи в `Schedule` и в таблицу (повторяемо и идемпотентно).
- `PlannerParam` — веса и пороги (своя таблица, не `tph_system.Settings`: тот читается один раз при импорте и только `int`).

## 4. Что известно про Google-таблицы (проверено 2026-10-20/21)

Правила листов — `gsheet.classify_tab(brand, name)`; листы центров = `Venue` (`manage.py schauto_seed_venues`: 19 центров JJ + 7 центров LL + 2 центра выездов «Экзотаг»).
Чтение: основной путь — сервисный аккаунт (`tabsource.ApiSource`: метаданные листов + `values:batchGet`); запасной, если ключ не настроен, — публичная ссылка (`…/export?format=csv&gid=<GID>`, список листов `…/htmlview`: `gsheet.list_tabs`/`read_tab_rows`, `tabsource.PublicSource`). Значения обоих путей совпадают ячейка в ячейку (сверено 2026-10-28 на 30 листах копий, ~64 тыс. ячеек, разбор тот же).
Копии таблиц повторяют прод: те же листы и те же gid.

**Таблица Joki Joya** (27 листов): берём 19 листов `<Центр> JJ`; 6 листов `… LL`, «ВЫЕЗДЫ» и «ВИДЕО ВСЕ ЦЕНТРЫ» игнорируем (остатки прежней общей таблицы).
Столбцы: [дата без заголовка], «Время», «время/дата сдачи обработки», «Заказчик» (не везде), «Именинник», «Ссылка на готовые фото», пожелания,
«Срок обработки», **«Ретушер»**, **«Фотограф»**, «Комментарии»; справа до 40 пустых столбцов. Нет номера заказа.
«Фотограф»/«Ретушер» — ники («Алиса», «Даша И», «Катя Львова»).

**Таблица Laserland** (10 листов): центры — «ГАГАРИНСКИЙ», «БЕГОВАЯ», «МЯКИНИНО», «КУНЦЕВО», «Каширка», «АЗОВСКИЙ», «Миниляндия» (пустой);
«ШОУ ВСЕ ЦЕНТРЫ» — игнорируем; «ВЫЕЗДЫ» — учитываем; «ВИДЕО ВСЕ ЦЕНТРЫ» — отложено.
- Столбцы центра: Дата, Время, **№ Банкета**, Заказчик, Телефон, Именинник, «ФОТО» (ссылка на готовые фото), пожелания, «Ссылка отправлена»,
  **«Фотограф»**. **«Ретушер» нет.** Лист «Каширка»: заголовком стала первая запись («М9706») — столбец даты определяется как «слева от Время».
- **«Фотограф» содержит телефон**: шаблон «Катерина 89688649620 [Имя Фамилия]» (1302 ячейки из ~1800 — только руководитель, т.е. заказ свободен; остальные — с дописанным
  фотографом; телефон руководителя в таблице бывает с опечатками, редко начинается на 8988) и «Дина 89180158874» → `parsers.strip_manager` + `clean_person` срезают маркер
  руководителя и цифры; в БД и логи телефоны не пишем.
- **№ Банкета — номер заказа** (заполнен в ~93% строк). Префикс кодирует центр (подтверждено): Г — Гагаринский, Б — Беговая, М — Мякинино, К — Кунцево,
  КШ — Каширка, А — Азовский; «Б» + буква центра = банкет («БГ», «БМ», «БК», «БА»; «ББ» — банкет Беговая). Посторонние значения («ФОТО…», «КОРП», «ЕЛКА»)
  — в ручной разбор. Пригодится для листа «ВИДЕО» (центр по префиксу) — пока не используется.
- «ВЫЕЗДЫ» (~24 заказа): столбец «адрес» — торговый центр («м. Новаторская, ТРЦ РИО Ленинский», «ТРЦ ГОРОД, Рязанский проспект», «ТРЦ Азовский»);
  часть адресов — не торговые центры, поэтому `place_raw` храним, только пока центр не сопоставлен.

**Общее**
- Раскладка столбцов **различается** между листами → столбцы ищутся **по названиям заголовков**, не по индексам (`sheetrows.find_columns`).
- Нет надёжного ID заказа → **отпечаток строки** (`parsers.row_fingerprint`): день.месяц + № банкета + заказчик/именинник (+ адрес для выездов) + номер
  повтора одинаковых строк. Время, исполнитель и год в отпечаток **не входят** (перенос времени и назначение не делают заказ «новым»). Из-за
  правки заказчика/даты в таблице заказ может стать «новым», а старый — «пропал из таблицы».
- **Год в датах не указан.** Листы упорядочены блоками месяцев **от новых к старым** (сверху будущие и текущие заказы; внутри месяца даты по возрастанию),
  разделители месяцев: «Январь 2024» (с годом у старых) или «ОКТЯБРЬ» (без года у свежих). `parsers.YearResolver` идёт по строкам сверху вниз и выбирает год,
  ближайший к опорной дате (медиана последних 5 строк — единичные «залётные» строки не сбивают); для первой строки листа берётся самая поздняя дата, не дальше
  100 дней вперёд от сегодня; разделитель с годом и явный год в ячейке сбрасывают опору. Проверено на копиях (без этого «ближайший к сегодня» год давал
  ложные заказы из прошлого года). Заброшенный лист, чьи верхние строки старше полугода, может сдвинуться — такие центры держим неактивными.
- **Адрес центра записан в служебной ячейке строки заголовков** почти каждого листа (23 из 26 центров; нет у Азовский LL, Миниляндия LL, Мега JJ) —
  `sheetrows.find_address` выбирает ячейку вне известных столбцов, где не меньше двух признаков адреса (ул., ш., пр-т, д., км, тц/трц/трк, м., МКАД); `manage.py schauto_seed_venues --fill-addresses`
  записывает их в пустые `Venue.address` (существующие адреса не трогает). Для «Экзотаг Рио» / «Экзотаг Город» адреса вводятся вручную (РИО Ленинский стоит в том же ТРЦ, что и «Рио JJ»).
- Время: ~98% ячеек разбираются. Поддерживаются «17:30-18:30», «20.00-21.00», «14-00-15-00», «17/30-18.30», «14:50--15:50», «15:50:00-16:50», «13;45-14:45»,
  «15 00-16:00», продление («+ доп час», «доп 30 мин», «+30 мин», «доп пол часа») и несколько интервалов (6% строк; на копиях в окне — 15 заказов, из них 13 с перерывом от часа): хранятся по отдельности в `slots`, в `notes` — перерывы и пометка «части можно
  отдать разным фотографам»; пересекающиеся интервалы объединяются. Продление ищется и в «Комментариях». Не разбираются («1 час», «2,5 часа», «12-13»,
  «ТУРНИР») → статус «Нужна ручная правка».
- Пометки после даты («23.10 МЕГА», «(перенос с 03.10)») сохраняются в `notes`. «МЕГА» на «Облака JJ» — историческая пометка (у Мега теперь свой лист), на планирование не влияет.
- Строки-разделители месяцев пропускаются; строки без времени пропускаются (счётчик в отчёте); окно загрузки по умолчанию: 14 дней назад — 120 вперёд.
- На копиях (окно 07.10.2026–18.02.2027, после правок 2026-10-23): 184 заказа (67 ждут исполнителя, 117 назначены в таблице, 0 на ручную правку), 21 неопознанное имя,
  оба заказа выездов сопоставились с «Экзотаг Рио»; остатков маркера руководителя нет; 15 заказов с несколькими интервалами (13 — с перерывом от часа).

## 5. Запись в таблицу и в график (этапы 4–5, `applying.py`, `sheetwrite.py`)

Доступ: сервисный аккаунт Google, JSON-ключ **вне репозитория**, путь — `SCHAUTO_GOOGLE_CREDENTIALS_FILE` в `.env` (на проде — том в `docker-compose`); библиотека `gspread` (в `pyproject.toml`/`poetry.lock`). Таблицам нужен доступ «Редактор» для e-mail сервисного аккаунта; тот же доступ используется и для чтения при загрузке заказов (см. ниже «Загрузка из таблиц»).

**Подтверждение проблем вручную** (`applying.py`: `Problem`, `Validation.row_soft/row_confirmed`, `save_confirmations`; экран `plan_detail`): блокирующие и подтверждаемые проблемы разведены (см. §2). Подтверждаемая проблема «не хватает минут» — одна на пару заказов фотографа: в обеих строках пары своя галочка, подтверждение общее (подпись симметрична). Форма шлёт `shown` (какие проблемы были на экране) и `confirm` (какие отмечены): показанная и не отмеченная теряет подтверждение, чужие/устаревшие/блокирующие подписи сервер игнорирует (подпись принимается, только если сейчас это действительно подтверждаемая проблема расчёта). Подтверждения обрабатываются в `plan_action` после правки исполнителей и до проверки, поэтому можно отметить галочки и сразу нажать «Применить распределение». Массово: `action=confirm_upto` + `upto` (минут). Журнал: `ImplEvents` `Schauto_Plan_Confirm` (кто, что) при подтверждении и снятии; при применении — текст в сообщении, в `ImplEvents` `Schauto_Plan_Apply` и в `PlanRun.apply_log[].confirmed`. Подтвердить можно только пока расчёт редактируем.

**Порядок применения** (`apply_plan`): проверки по БД (`validate_plan`) → предпроверка таблиц **без записи** (`sheetwrite.prepare`: строка найдена, дата/время те же, ячейка пуста) → блокировка `PlanRun.status='applying'` (защита от двойного нажатия) → запись в таблицы (`sheetwrite.commit` на прочитанном при предпроверке) → запись в `Schedule` и обновление заказов (`status=assigned`, `photographer`) в одной транзакции → итоговый статус `applied` / `partial` / `draft`. Любая неудача проверок = в таблицах и в графике ничего не изменено.

**Запись в ячейку «Фотограф»** (ошибка здесь — чужие данные в живой таблице): строка ищется заново по **отпечатку** (не по сохранённому номеру — строки сдвигаются); дата и время строки должны совпадать с заказом; ячейка должна быть пуста от исполнителя — в Laserland в ней по умолчанию «Катерина 89688649620», имя **дописывается после** (`Катерина 89688649620 Иван Петров`); вписанный после загрузки другой исполнитель не перезаписывается (конфликт, строка остаётся без записи); то же имя — `already` (идемпотентно); формат «Имя Фамилия» = `str(Staff)`. Лист «ВЫЕЗДЫ» (Laserland) обрабатывается так же. Одна запись `batch_update` на лист.

**Ретушёр (только таблица JJ)**: если исполнитель заказа обрабатывает фото сам (`Staff.retouches_own`), его имя пишется и в «Ретушер» **той же пакетной записью**, но только в **пустую** ячейку; уже указанный ретушёр (`other`) и «исходники» (`originals`, ретушь не нужна) остаются как есть с замечанием; то же имя — `already`; непонятное содержимое (`?`) не перезаписывается. Фотограф с `retouches_own=False` — ретушёр не вписывается (`not_own`), в итоге замечание «нужен отдельный ретушёр». Запоминается в `Assignment.ret_status/ret_before/ret_after`, у заказа ставятся `retoucher`/`retoucher_raw` (импорт тот же `Имя Фамилия` сопоставляет сам). В откате «Ретушер» возвращается так же точно, но **независимо**: изменённая после записи — замечание, откат заказа от неё не зависит; если «Фотограф» в конфликте, «Ретушер» тоже остаётся.

**Производительность и лимиты Google** (оптимизировано 2026-10-28, замеры на 29 заказах / 31 части / 14 листах / 2 таблицах). Было: проверка 18,4 с, применение ≈48 с и ~74 запроса к Google (~60 чтений, то есть **упирались в лимит 60 чтений в минуту**), потому что `gspread.get_worksheet_by_id` при каждом вызове заново скачивает метаданные всей таблицы, листы читались по одному, а применение читало всё дважды. Стало: **проверка 1,4–2,8 с (2 запроса), применение 3,4–4,5 с (6 запросов: 4 чтения + 2 записи), откат 2,9–4,2 с**; число запросов не зависит от числа листов. Как: (1) обращаемся к Google только через HTTP-клиент `gspread` (`GoogleClient/GoogleBook` в `sheetwrite.py`), а не через его объекты листов; (2) **на таблицу — 3 запроса**: чтение всех нужных листов одним `values:batchGet`, перечитывание целевых строк одним `batchGet`, запись всех ячеек одним `values:batchUpdate`; (3) листы читаются **по названию, сохранённому при загрузке** — метаданные (gid → название) нужны только если лист переименовали или удалили (Google отвечает 400 «Unable to parse range», тогда запасной путь по `sheet_gid`); верность строки обеспечивают отпечаток и сверка строки, а не название листа; (4) проверка и запись делят одно чтение (`prepare` → `commit`); перед записью целевые строки **перечитываются и сверяются** (первые 30 ячеек): изменилась с момента проверки — в неё не пишем (`changed`), так что сдвиг строк не приведёт к записи не туда; (5) таблицы разных брендов обрабатываются **параллельно** (2 потока); (6) клиент Google живёт в процессе по одному на таблицу (токен и соединение переиспользуются, ~1 с экономии на повторном нажатии), обращения под блокировкой, после ошибки клиент выбрасывается; (7) БД: пакетные `bulk_update` заказов, существующие смены подгружаются одним запросом, проверки отката («есть продажи / расчёт ЗП / другой расчёт») — тремя общими запросами вместо нескольких на смену (откат 143 → 66 запросов, без сети ≈ 0,1 с). Остаток времени — задержки сети Google (≈0,3–1,5 с на запрос, три запроса по цепочке). Память: пик ≈14 МБ на 30 тыс. ячеек. Ошибка 429 показывается понятным текстом («подождите минуту и повторите»); повтор безопасен (идемпотентно).

**Архитектурные ограничения, которые остаются** (сознательно не менялись): (а) применение и откат выполняются **синхронно в веб-запросе** (на проде `runserver`, один процесс, 1 ядро): на время запроса занят поток; у nginx нет своих таймаутов, действует умолчание **60 с на ответ** (`docker/nginx/nginx.conf`) — при ~4 с запас большой, но если Google «залипнет», пользователь увидит 504, хотя запись могла пройти; применение идемпотентно, повторное нажатие безопасно; (б) если потребуются сотни заказов за раз, следующий шаг — вынести применение в Celery (воркер общий с OCR, `-c 1`: долгая OCR-задача задержит применение) с опросом статуса на странице; пока не нужно; (в) задержки Google (три запроса по цепочке на таблицу) — нижний предел по времени; (г) параллельные нажатия двух менеджеров по одной таблице обращаются к Google по очереди (блокировка клиента), а не одновременно; (д) «Загрузить из таблиц» тоже синхронна в веб-запросе (≈2,5–5 с при двух запросах на таблицу; см. ниже); (е) на проде `DEBUG=True` и debug-toolbar (§10 корневого CLAUDE.md): при показе тулбара ответ страницы расчёта вырастает с ~110 до ~480 КБ и рендерится вдвое дольше; за nginx IP клиента не `127.0.0.1`, так что тулбар не показывается, но `DEBUG=True` остаётся лишней нагрузкой.

**Загрузка из таблиц** (оптимизировано 2026-10-28, `importer.run_import` + `tabsource.py`). Было: публичный CSV по одному запросу на лист — **27 запросов** (2 списка листов + 25 листов), 6 потоков, **12,6 с**, 1,45 МБ. Стало: чтение через сервисный аккаунт — **4 запроса** (на таблицу: метаданные листов `fields=sheets.properties(sheetId,title,hidden)` + **один** `values:batchGet` всех нужных листов; таблицы брендов читаются параллельно): **≈2,6 с при открытом клиенте и ≈4,6 с на первом обращении процесса** (вход в Google), число запросов не зависит от числа листов; пик памяти чтения ≈9 МБ; квота Google (60 чтений/мин) расходуется на 4 запроса за загрузку. Функционал не потерян: разбор тот же (`parse_rows`), номер строки = индекс + 1 в обоих путях, скрытые листы пропускаются как на публичной странице, отчёт по листам прежний, один сбойный бренд не роняет второй (одна ошибка на таблицу, а не по записи на лист), сбой клиента выбрасывает его из общего (`googleapi.forget_client`), 429 и «лист переименовали во время загрузки» дают понятный текст. Проверка: на копиях таблиц состояние `PhotoOrder` после загрузки через API и через CSV побайтно совпало (178 заказов, один хэш), повторная загрузка идемпотентна; кнопка в интерфейсе — те же сообщения. **Выбор источника**: `tabsource.default_source()` — сервисный аккаунт, если настроен `SCHAUTO_GOOGLE_CREDENTIALS_FILE` (ключ существует), иначе публичная ссылка с примечанием в отчёте и `ImplEvents` («чтение идёт по публичной ссылке, это медленнее»); при настроенном ключе, но сбое чтения публичный путь молча **не** подставляется (ошибка видна в отчёте). Команда `schauto_seed_venues` (в т.ч. `--fill-addresses`) читает через тот же источник. Транспорт Google (`GoogleBook`, общий клиент, блокировки, **сетевые таймауты (10 с соединение / 40 с ответ)**) вынесен в `googleapi.py` и общий для чтения и записи. Остаточные ограничения: два последовательных запроса на таблицу (метаданные → значения, ≈0,8 + 1,3 с) — нижний предел без отказа от проверки «лист есть в таблице» и номеров листов (gid), которые нужны применению; читаются листы целиком (≈64 тыс. ячеек на копиях — мелочь, но при росте истории листов объём растёт линейно, а окно дат можно ограничить только после разбора сверху вниз — год в датах не указан, §4); загрузка по-прежнему в веб-запросе, как и применение (см. выше).

**Запись в `Schedule`**: для каждого вписанного заказа в центре с `Venue.store` — `get_or_create(staff, date, store)` с `position='Выездной фотограф'`, `work_time` = начало первого заказа фотографа в этот день на этой точке (`HH:MM`); уже существующая смена не меняется (если её роль другая — предупреждение). Центры без фототочки — `schedule_status='no_store'`. Запись влияет на деньги (`SalesForm`, `sal_calc` ветвится по роли «Выездной фотограф»), поэтому только после проверок и подтверждения кнопкой.

**Заказ, разделённый между фотографами** (2026-10-28): в ячейку пишутся имена через « + » (`Иван Петров + Мария Сидорова`, как пишут в таблицах), порядок — по частям. Импорт разбирает такую ячейку (`parsers.split_people`: разделители «+», запятая, «;», «&», строчное « и »; «+» в конце — **пометка в таблице, а не второй человек**: в копиях 138 ячеек вида «Екатерина Львова+ - -», они остаются с одним именем; ссылки и «/» не разделители): каждое имя сопоставляется отдельно (`importer.resolve_people_and_place`), игнорируемые («штат») отбрасываются. Один человек — `PhotoOrder.photographer`; несколько — `photographer` пуст, сопоставленные сотрудники в `PhotoOrder.photographers` (`importer.sync_team`), `photographer_raw` = «Имя + Имя». На экране «Сопоставления» несопоставленные имена показываются **по одному**, а не парой. **Занятость** (`planning.fixed_parts`): каждый участник занят во всех частях заказа (в ячейке не сказано, кто какую часть снимает), но свободен в перерыве; если заказ распределял расчёт, берутся точные части из применённых `Assignment`. Заказ учитывается в дневном лимите и в «знакомстве с центром» каждого участника. Заказ с именами, ни одно из которых не сопоставлено, остаётся «неизвестной занятостью» (предупреждение в расчёте). Проверка применения: `sheetwrite` считает «то же» при тех же людях в любом порядке (`parsers.same_people`), иначе — конфликт. Откат очищает `photographers`. ЗП за части — не определена (отдельный этап).

**Удаление черновика** (2026-10-28; кнопка «Удалить распределение» справа в шапке страницы расчёта, `applying.delete_plan`, право `run_planning`): удаляется расчёт вместе с назначениями, объяснениями и подтверждениями; Google-таблицы, график работы и заказы не затрагиваются (черновик в них ничего не менял). Удалить можно только `PlanRun.deletable` — статус «Черновик» и ни одно назначение не вписано в таблицу (в т.ч. после отката применения расчёт снова черновик и удаляется); «Применён», «Применён частично», «Применяется», «Откатывается» — нельзя (сначала «Откатить применение»), кнопка скрыта, а POST отклоняется с пояснением. Подтверждение — `confirm()` в браузере; после удаления возврат к списку расчётов. Журнал: `ImplEvents` `Schauto_Plan_Delete` (итог) плюс общие `Delete_rec_from_planrun`/`Delete_rec_from_assignment` от сигнала проекта — на каждое назначение по записи (расчёт из 28 назначений ≈ 30 событий, ≈ 40 КБ).

**Откат применения** (кнопка «Откатить применение» на странице расчёта, `applying.rollback_plan`, право `run_planning`; доступна для «Применён» и «Применён частично»). Для каждого заказа, который записало это применение (`Assignment.sheet_status='written'`): ячейка «Фотограф» возвращается к состоянию **до записи** (`Assignment.sheet_before`/`sheet_after` запоминаются при записи) — но **только если в ячейке ровно то, что вписали мы**; изменённая после записи — конфликт, не трогаем; строки в таблице нет — откатывать нечего (замечание); строка ищется по отпечатку. Дальше по тому же заказу: заказ снова `open`; смена в `Schedule`, **созданная** этим применением, удаляется, **кроме** случаев: роль или время работы изменены вручную, на смене есть продажи (`Sales` с этим сотрудником, точкой и датой) или расчёт зарплаты (`Salary`), смену использует другой расчёт, часть заказов смены не откатилась — тогда смена остаётся с пояснением. Имя, которое уже стояло в таблице до применения (`already`), не трогается; существовавшие смены (`exists`) не удаляются. Всё по каждому заказу независимо: откат — либо целиком (расчёт снова `draft`, его можно поправить и применить заново), либо частично (`partial`, оставшееся с причинами в строках; повтор «Откатить» доделывает). Недоступный Google блокирует откат до любых изменений. История применений и откатов — внизу страницы расчёта.

**Повторное применение** безопасно: уже вписанное (`sheet_status` written/already) пропускается; сбой по части заказов даёт статус «Применён частично», исправляете причину и нажимаете «Применить» ещё раз. `Assignment.schedule` / `schedule_status='created'` хранят, что создано (на этом строится откат). Если процесс умер во время применения или отката, расчёт остаётся в статусе `applying`/`rolling_back` — сбросить в админке на `applied`/`partial`/`draft`.

## 6. Алгоритм (этап 3: `availability.py`, `planner.py`, `planning.py`)

**Разбор доступности** (`availability.parse_availability`, чистая функция): окна времени в минутах от полуночи. «с/после/от T» → (T, 24:00); «до T» → (0, T); «T1-T2», «с T1 до T2» → окно; несколько окон объединяются; «Занят T1-T2» → всё, кроме этого интервала; голое время («15:30») = «с 15:30» (с пометкой); «T1/T2» → позднее; скобки игнорируются; латинская «c» = «с»; «весь день», «с утра», пусто → весь день. Нераспознанное → `ok=False`, окон нет. На 96 реальных значениях разобрано 95 (не разобрано «ПОЛ ДНЯ»).

**Вход** (`planning.collect`): заказы со статусом `open` в периоде и в **активных** центрах → части (`PhotoOrder.parts`, продление — к концу последней части); фотографы: `staff_type='Выездной'`, «Работает», заданы навык и лимит (иначе предупреждение, в расчёте не участвует); доступность дня — по графику выходов: отпуск/отгул/больничный закрывают день, всё остальное (в т.ч. нет записи) открывает, время — по тексту `time_availiable`; назначенное вручную (`assigned` и сопоставленный фотограф) — занятость, которую не трогаем; знакомство с центром = заказы фотографа в таблицах до периода + смены в `Schedule` за год на фототочке центра; маршруты — минимум по вариантам пары.

**Жёсткие ограничения**: доступность в день (окно должно целиком накрывать часть); не больше `Staff.max_orders_per_day` заказов в день (части одного заказа — один заказ; ручные учитываются); нет пересечений с любым заказом дня; между частями **разных** заказов у соседей по времени: дорога (минимум по вариантам; для центра в том же здании 0) + буфер 15 мин; нет маршрута → консервативные 90 мин и пометка в плане. Части одного заказа вплотную друг к другу — без запаса.

**Мягкие (штрафы, `PlannerConfig`, меньше — лучше)**: сложность части = сложность центра + 1 за каждый час сверх первого (потолок +2) + 0,5 за продление; нехватка навыка 4,5/балл, избыток 0,3/балл; фотограф не работал в центре +2; нагрузка недели `100·(заказов на неделе/(2·доступные дни недели·вес навыка))²`, вес = навык² к среднему (выше навык — больше заказов); **неделя — целая (пн–вс), а не период расчёта** (2026-10-28, решение владельца: распределение обычно запускают на один день вперёд, по одному дню нагрузку недели не узнать): к заказам внутри периода добавляются заказы фотографа на остальные дни недели **из «Заказов»** (`planning.week_load`: статус «Назначен», один исполнитель или все из `photographers`, вне периода — и раньше, и позже; заказы периода не считаются дважды), а «доступные дни» — дни недели без отпуска/отгула/больничного по графику выходов за **всю** неделю (день без записи доступен, выходные тоже); считается прирост штрафа от лишнего заказа (штраф растёт по квадрату — загруженному лишний заказ дороже); **дневной лимит в ёмкость не входит** (это жёсткий потолок, иначе человек с малым лимитом, но высоким навыком недогружается — так было в первой версии); при равных штрафах побеждает более сильный (разница штрафов округляется до 1e-9, чтобы шум вычислений не решал ничью); дорога 0,05/мин; лишний исполнитель одного заказа +6.

**Метод**: «сначала самые стеснённые» (меньше всего подходящих фотографов, потом сложнее) → к фотографу с минимальным приростом штрафа → проходы локальных улучшений (перенос, обмен, пристройка оставшихся, вытеснение чужой части) до отсутствия улучшений (≤30 проходов). Детерминированно (порядок входа не важен). На реальных данных (28–36 частей, 7 фотографов) — 0,1 с; 150 частей на случайном сценарии — доли секунды.

**Объяснения** (`PlanEntry`, хранятся в `Assignment`): почему этот фотограф (навык vs сложность, знакомство с центром, соседние заказы дня и запас на дорогу, нагрузка недели (из них — вне периода расчёта, по «Заказам»; ёмкость недели; дневной лимит — жёсткий потолок), сколько фотографов подходило, кто лучшая замена и на сколько хуже), почему не остальные (причина по каждому), для нераспределённого — причина по каждому фотографу. Для заказов со статусом `needs_fix`, `gone` и неизвестным центром планирование не выполняется (предупреждение). Ретушёр и видео этапом 3 не планируются.

**Проверка готового распределения** (`planner.find_problems` / `sequence_problems`; `find_conflicts` и `sequence_problem` — обёртки «первая причина») — то же правило «пересечения и дорога+буфер», что и в алгоритме, применяется к ручным правкам; `Rejection` для нехватки времени несёт пару частей, «нужно» и «есть» минут (по ним строится подпись подтверждения). Пересечение заказов — блокирующая причина, нехватка минут на дорогу — подтверждаемая (§2).

**Известные упрощения**: смена в `Schedule` (в т.ч. на штатной точке) не блокирует выездного; доступность проверяется только на интервал заказа (дорога до него в окно не входит); вес навыка и штрафы подобраны разумно, но не откалиброваны на реальных планах — править `PlannerConfig` по итогам первых расчётов; параметры пока константы кода (таблица `PlannerParam` — только если понадобится править из UI).

## 7. Подводные камни основной системы

- `tph_system.views.update_schedule` **удаляет все записи сотрудника за день и создаёт заново** — не использовать для автозаписи; писать
  `Schedule.update_or_create(staff, date, store)` и хранить связь `Assignment → Schedule` для отката. Пишем только для `Venue.store` (см. §2).
- Запись в `Schedule` влияет на деньги: `SalesForm` требует, чтобы фотограф стоял в графике точки, а `sal_calc` ветвится по
  `position == 'Выездной фотограф'` (`funcs.py`). Поэтому запись — только после явного подтверждения, с откатом и в `ImplEvents`.
- `Schedule` unique(staff, date, store): два заказа выездного на одной точке в день — одна запись.
- Каждая бизнес-операция пишет `ImplEvents` (типы `Schauto_*`). Права — через `Meta.permissions` + миграция, напомнить выдать группе.
- Стандартный `manage.py test` на dev-машине падает: у роли Postgres нет CREATEDB. Тесты гонять на SQLite со скретч-настройками
  (в импорте `tph_system.funcs` читается таблица `Settings` — нужна пустая таблица-заглушка) либо выдать роли `CREATEDB`.
- Импорт читает листы через сервисный аккаунт (4 запроса, ≈2,5–5 с на обе таблицы) в HTTP-запросе; публичный запасной путь — ~25 запросов в 6 потоках, 10–25 с. Если станет медленно — вынести в Celery (воркер общий с OCR, `-c 1`).
- Сеть и разбор отделены от БД: `importer.run_import(lister=..., fetcher=...)` (публичное чтение) и `source=` (готовый `ApiSource(factory)` с подменой клиента Google) принимают подмены — так он тестируется без сети; в тестах с настроенным ключом `default_source` подменять обязательно (иначе пойдёт реальный запрос).

Из `TPS/Dj_TPS`: `manage.py migrate` (применит `tph_system/0009`, `schauto/0001`–`0012`) → выдать группам права `schauto.*` (в т.ч. `import_orders`, **`view_planrun` и `run_planning`** для «Распределить») →

действующие фототочки, оставит неактивным центр с закрытой точкой (Азовский LL), заведёт «Экзотаг Рио» / «Экзотаг Город» →

истории графика) → маршруты: «Маршруты» → «Скачать CSV (шаблон)», заполнить «Минут», «Загрузить из CSV» → «Заказы» → «Загрузить из таблиц» →
«Сопоставления» (ники → сотрудники, адреса выездов → центры) → при необходимости повторить загрузку (она идемпотентна).
**`.env` сейчас содержит ID копий таблиц** (прод-ID закомментированы) — перед использованием на проде заменить на прод-ID.

**Тесты** (389, без сети и Postgres): стандартный `manage.py test` не запускается (у роли Postgres нет CREATEDB), поэтому на SQLite:
1. файл `<dir>/schauto_sqlite_settings.py`: `from Dj_TPS.settings import *` + `DATABASES = {'default': {'ENGINE': 'django.db.backends.sqlite3', 'NAME': '<dir>/stub.sqlite3'}}`;
2. заглушка для чтения `Settings` при импорте `tph_system.funcs`: `sqlite3 <dir>/stub.sqlite3 "create table tph_system_settings (id integer primary key, param text, value text)"`;
3. из `Dj_TPS`: `PYTHONPATH=<dir> poetry run python manage.py test schauto --settings=schauto_sqlite_settings --noinput`.
Тестовая БД — в памяти; рабочая БД и Google-таблицы не затрагиваются (сеть в тестах подменяется, см. §7).

## 11. Маршруты: как заполнить (предложение от 2026-10-23, ждёт решения владельца)

Требование: время A→B **как в Яндекс Картах, режим общественного транспорта** (метро, электрички, автобусы, пешком), без запаса — запас учитывает планировщик.
Адреса центров уже в `Venue.address` (см. §4), по ним строятся ссылки в карты и геокодирование.
Объём: ~27 активных центров (19 JJ + 6 LL + 2 Экзотаг) → ~700 направленных пар (~350 без учёта направления); важна лишь часть — соседние центры.
Проверено поиском и чтением документации (2026-10-23):
- **Яндекс «Матрица расстояний»** считает общественный транспорт, отдаёт длину и время (без маршрута). Бесплатного тарифа/теста **нет**; 1 элемент матрицы = 1 запрос.
  По странице тарифов: помесячно только лицензия *basic* от 20 800 ₽/мес (1000 запросов/сутки), которая **не разрешает сохранять данные**; лицензия *advanced*
  (сохранение разрешено) — от 226 200 ₽/год. Страница оговаривает, что это не оферта; условия нужно уточнять у Яндекса.
- **2ГИС Public Transport API** (`routing.api.2gis.com/public_transport/2.0`): метро, автобус, электричка и др.; ключ — демо или платный из Platform Manager. Страницы документации
  при проверке не открылись (404), поэтому лимиты демо-ключа, условия сохранения данных и покрытие Москвы **не проверены** — перед выбором нужно проверить на реальном ключе.
- Бесплатный JS API Яндекса рассчитан на показ маршрутов на карте; собирать им данные в БД условия не предполагают — не использовать.
